# Tracker: releases, bugs, requests and shared features

The catalog says what a product does and where each behaviour is shipped. The tracker
adds what is planned and what is wrong: releases with their target windows, bug reports,
feature requests, and features shared with other apps. One catalog per app; a suite file
joins several apps into one view.

Nothing here is a second feature list. Implemented features are catalog entries whose
platform status is `shipped`; planned features are entries still `missing` or `partial`,
or requests not yet written as entries. The tracker only points at them.

## Files

Optional, beside `catalog.toml`:

```text
spec/product/
  catalog.toml
  catalog/*.yaml
  tracker/releases.yaml   # optional
  tracker/issues.yaml     # optional
  tracker/log.jsonl       # optional, append-only facts; see Log
  tracker.md              # generated by `concordance track`
```

Both files are nonempty arrays, parsed with the same strict rules as area files
(unknown fields, duplicate keys and invalid types are errors). A list or map field
written as `null` (for example `carries: null` or `builds: ~`) is an invalid type: omit
the field or write `[]` or `{}`. Optional scalars such as `duplicate_of` may be `null`.
A catalog without a
`tracker/` directory is valid and `track` reports only gaps and shared features.

### Releases

```yaml
- id: "1.2.0"
  state: candidate          # idea | planned | candidate | in-review | released | pulled
  title: Sync between devices
  why: Holiday listening; first public Android beta   # the reason for the timing
  window: { from: 2026-11-20, to: 2026-12-05 }        # target, never a gate
  released: 2026-12-03      # required when state is released; forbidden before
  builds: { ios: "44", android: "126" }               # platform -> build label
  carries: [sync.join-by-qr, bug.home-recovery-blank, request.reuse-identity]
  notes: []
```

`id` is a version or other label, unique within the catalog. Every `carries` item must
resolve to a catalog entry ID or an issue ID. `builds` keys must be configured platforms.
`window.from` must not be after `window.to`. Dates are `YYYY-MM-DD`.

### Issues

```yaml
- id: bug.home-recovery-blank
  kind: bug                 # bug | request
  title: Home stays blank after recovery
  summary: After restoring a library, Home shows nothing until relaunch.
  state: fixed              # open | planned | in-progress | fixed | verified | closed | wont-fix | duplicate
  impact: high              # critical | high | medium | low (same scale as entries)
  reported: 2026-11-21
  source: [device, "https://projects.toolsperson.com/board#/project:galley/item/..."]
  platforms: [ios]
  entries: [home.show-library]
  release: "1.2.0"
  evidence: ["test-taupe-colophon-05-notes.py 13/13"]
  duplicate_of: null        # an issue ID; required when state is duplicate
  notes: []
```

The ID prefix matches `kind`: `bug.` or `request.`, then lowercase letters, numbers and
hyphens. IDs are unique across issues and must not collide with entry IDs.
`entries` must exist; `release` must name a release; `platforms` must be configured.
`verified` requires nonempty `evidence`. `duplicate` requires `duplicate_of` naming
another issue. `title` and `kind` are required; everything else is optional.

### Shared features

An entry may name the same feature in other apps:

```yaml
- id: player.skip-forward
  shared_with: ["marginalia:player.skip-forward"]
```

Each value is `<app>:<entry-id>`. A single catalog checks only the syntax; `suite`
resolves it against the other apps and lists any it cannot resolve.

## Log

`tracker/log.jsonl` records facts; the YAML files hold plans. Agents and tools append to
it with `concordance log`, never by hand, and `track` and `suite` derive states from it.
A catalog without a log behaves exactly as described above.

### Events

One JSON object per line, keys in this order, empty optional fields omitted:

```json
{"id":"5f0c3c1a9d2e7b44","kind":"fixed","subject":"bug.home-blank","at":"2026-11-21T10:02:11Z","by":"Alice","commit":"9e1c…"}
```

| Kind | Subject | Fields |
| --- | --- | --- |
| `reported` | issue | `title` (required), `entries`, `platforms`, `impact`, `source` |
| `fixed` | issue | `commit` |
| `verified` | issue | `evidence` (nonempty), optional `commit` |
| `reopened` | issue | `reason` |
| `uploaded` | release | `platform`, `build`, optional `commit` |
| `released` | release | `date` (YYYY-MM-DD), optional `platform`, `commit` |
| `pulled` | release | `reason` |

`at` is UTC to the second (`YYYY-MM-DDTHH:MM:SSZ`); `by` is who recorded the fact. The
issue kind comes from the subject's prefix (`bug.` or `request.`). `id` is an FNV-1a 64
hash (16 hex digits) of the kind, the subject and the fields that make the fact distinct:
nothing more for `reported` (one report per issue); `commit` for `fixed`; `by`, `evidence`
and `commit` for `verified`; `reason` and `at` for `reopened`; `platform` and `build` for
`uploaded`; `platform` for `released`; `reason` for `pulled`. Appending an event whose id
is already in the log does nothing and prints `already recorded`.

Parsing is strict: unknown fields, missing or forbidden fields for the kind, malformed
times and dates, blank lines, an `id` that does not match the content, duplicate ids, and
references to unknown issues, entries or platforms are errors that name the line
(`tracker/log.jsonl:7`). The `log` commands refuse to append while the log has errors.

### Commands

```sh
concordance log report bug|request "Title" [--entry ID]... [--platform P]... [--impact I] [--source S]...
concordance log fixed ISSUE --commit SHA
concordance log verified ISSUE --evidence TEXT... --by WHO
concordance log reopened ISSUE --reason TEXT
concordance log uploaded RELEASE --platform P --build B [--commit SHA]
concordance log released RELEASE [--platform P] [--date D] [--commit SHA]
concordance log pulled RELEASE --reason TEXT
concordance log scan-git [--repo DIR] [--since REF]
```

Every `log` command takes `--catalog DIR` (default: `$CONCORDANCE_CATALOG`, then the
current directory if it holds `catalog.toml`, then the only `spec/*/catalog.toml` below
it), `--by WHO` (default: `$CONCORDANCE_ACTOR`, then `git config user.name` in the
repository, then `unknown`; `verified` requires it) and `--at` (UTC time or date; default
now). Commits given to `fixed`, `verified`, `uploaded` and `released` are expanded to full
hashes when git knows them. `released` without `--date` uses the day of `--at`.

`report` prints the issue id: `bug.` or `request.` plus a slug of the title (lowercase
ASCII letters and digits joined by hyphens, at most 48 characters), suffixed `-2`, `-3`, …
when issues.yaml, an entry or the log already uses it. A title that an existing issue of
the same kind already has reuses that issue's id, so reporting the same thing twice is a
no-op, and reporting an issues.yaml title adds a report for it.

### `scan-git`

Reads commits (oldest first; `REF..HEAD` with `--since`) in the catalog's `repo_root`
(or `--repo`) and appends what their trailers state, with the commit's author as `by` and
its commit time as `at`:

```text
Fixes: bug.home-blank, bug.player-stall
Verifies: bug.home-blank (test-taupe-colophon-05-notes.py 13/13)
Reports: request.reuse-identity
```

Trailer values list IDs separated by commas, each optionally followed by evidence in
parentheses. `Fixes:` records `fixed` with the commit; `Verifies:` records `verified` with
the evidence (or `commit <hash>` when none is given) and the commit; `Reports:` records a
`reported` event for an issue that already exists. IDs that are not known issues are
skipped with a warning on stderr.

Tags matching a pattern in catalog.toml record `released` events for the version, with the
tag's commit, dated by the tag's creator date (the tagger date of an annotated tag, the
commit date of a lightweight one) and recorded by the tagger or commit author:

```toml
[tracker]
tag_pattern = ["ios/v{version}", "taupe-{version}"]   # or one string
```

Each pattern has exactly one `{version}` (which must start with a digit); `*` matches
within one path segment. With `--since`, tags whose commit the ref already contains are
skipped. Rescanning records nothing new.

### Derived states

`track` and `suite` replay the log in time order (file order breaks ties):

- **Issues** reported only in the log appear beside issues.yaml ones (`reported` is the
  day of the report). An issue is **open** until a fix is recorded, **fixed** with a fix
  commit, and **verified** when someone other than every fixer records a verification;
  the verifying evidence joins the issue's evidence. A fixer's own check does not count:
  the issue stays fixed and Unverified lists it as `self-verified by WHO`. **Shipped** is
  shown instead of verified when a released release's `released` commit contains a fix
  commit (`git merge-base --is-ancestor`); an unverified fix that shipped is listed in
  Unverified with `release R has shipped`. **Reopened** discards earlier fixes and
  verifications. When git is missing or a commit is unknown, shipping is not checked and a
  warning says so.
- **Releases**: uploaded builds replace the platform's build from releases.yaml; the last
  `released` or `pulled` event sets the state, and the earliest `released` date becomes
  `released`. A release with uploads only is a candidate. Releases only in the log appear
  beside releases.yaml ones. releases.yaml `state: released` without log events stands.
- **Declared and derived**: a derived state replaces the declared one. For issues, only
  `fixed`, `verified` and `reopened` events derive a state (a report alone keeps the
  declared one); `closed`, `wont-fix` and `duplicate` stand, since the log cannot express
  them; `planned` and `in-progress` stand while nothing is fixed. Any other difference from
  a declared `state` (an omitted `state` declares nothing) becomes a warning, as do a
  declared release state, released date or build that the log contradicts. Warnings are a
  `## Warnings` section after the Summary and a `warnings` list in JSON (in `suite`, per
  app); both are omitted when there are none.

## Commands

```sh
concordance track spec/product [--out tracker.md] [--check] [--format markdown|json] [--today YYYY-MM-DD]
concordance suite suite.toml   [--out suite.md]   [--check] [--format markdown|json] [--today YYYY-MM-DD]
```

`track` writes `<dir>/tracker.md` by default (`<dir>/tracker.json` with
`--format json`); `--check` compares exactly and never writes, like `report --check`, and
when the file is stale prints the command that regenerates it, with the same catalog
directory, `--format` and `--today`. Every Markdown table cell escapes `|` and flattens
line breaks. Output contains no relative time unless `--today` is
given, so a checked file does not go stale by itself. With `--today`, releases whose
window has ended without release are marked overdue and upcoming beats are listed.

`track` sections, in order:

1. **Summary**: last release, next release and its window, open bugs by impact, open
   requests, unverified items, and gap counts per platform, written compactly as
   `android 34 missing · 135 partial · 14 stale; ios none` (zero parts dropped; `none`
   when no platform has gaps). Gaps count `missing`, `partial` and `stale` entries.
2. **Releases**: newest planned first (in-review, candidate, planned, idea), then the
   last two released or pulled. Each lists its window, why, builds, and every carried
   item with its current status: an entry's status on each platform, or an issue's state.
   A release's readiness counts carried items that are not shipped on every platform the
   release builds (the report's baseline and target platforms when `builds` is empty;
   `not-applicable` counts as done), and issues that are not `verified` or `closed`.
   A release without a window shows no window line.
3. **Bugs** and **Requests**: open ones (not verified, closed, wont-fix or duplicate),
   ordered by impact, then reported date, then ID.
4. **Unverified**: issues marked `fixed` without evidence, and fixed issues whose
   release has shipped while they stay unverified. A shipped release is the issue's own
   `release` or any `released` release that carries it; pulled releases do not count.
5. **Gaps**: for each platform, counts of missing, partial and stale entries and the
   first five in work-queue order. When the dependency-ordered work queue cannot be
   built (for example a dependency has no record on that platform), the list falls back
   to impact order and says so with the reason; JSON carries `order` (`work-queue` or
   `impact`) and `order_note`.
6. **Shared**: entries with `shared_with`.

`--format json` emits the same content as one object (stable key order) for boards and
other tools; Galley reads this.

### Suite file

```toml
title = "LUFF suite"

[apps.taupe]
catalog = "../Marginalia/spec/taupe" # relative to this file's real location
label = "Taupe"

[apps.chase]
catalog = "chase/spec"

[[beats]]
date = 2027-06-07
title = "WWDC 2027"
why = "New OS features announced; plan adoption for September."
```

Catalog paths are relative to the suite file's real location: a symlinked `suite.toml`
resolves them from its target. `..` and absolute paths are allowed, since apps usually
live in sibling repositories. The default output (`suite.md`, or `suite.json` with
`--format json`) is written beside the suite path as given.

`suite` loads every catalog (structural validation only; no evidence checks), then
writes: one row per app (last release, next release and window, open bugs with
critical/high counts, open requests, unverified, gaps per platform in the same compact
form as the track summary); upcoming beats with
the releases whose window has at least one day in the 60 days before each beat, strictly
before it (`window.from` earlier than the beat and `window.to` no earlier than 60 days
before it; needs `--today` to
filter past beats; otherwise all beats are listed); and a shared-features table showing,
for each shared feature, every app's entry and its baseline status, with unresolved
references flagged.
